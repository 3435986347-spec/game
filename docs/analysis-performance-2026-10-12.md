# 分析复查与性能实测（2026-10-12）

本轮提高了已有搜索结果的利用率，并修复评分、飞刀识别和实时连接的问题。引擎仍使用本机 Pikafish，4 线程、256 MiB Hash；提示、复盘和训练每次搜索 1500 ms，全力 AI 4000 ms，其余教学级别保留节点预算。

## 已修复的问题

| 问题 | 修复与回归 |
| --- | --- |
| 截短主要变化，把正常兑子或后续另一着弃子误称为当前着法的飞刀 | 检查完整合法变化；通用标注要求当前着法直接献子或暴露己子，并有对方立即接受的证据；正式棋谱名称仍优先匹配 |
| 走了引擎最佳着，即使按规则已进入和棋或败局仍免除损失 | 终局结果优先；每步评级、准确率、关键时刻及接口统一处理；旧复盘使用保存的分析证据升级，不重新搜索 |
| 升级旧复盘时可能覆盖并发新增的讲解 | 用原报告摘要做并发检查；评级未变的行保留数据库最新讲解，变更行清除过期讲解 |
| 快速切换同一棋盘的不同历史或连接重建时收到旧结果 | 前后端增加请求编号；旧连接、旧请求和旧目标结果不能覆盖当前分析；目标消失时停止搜索 |
| 多页面同时开始分析，暂停通知带错请求编号或遗漏中间搜索 | 旧请求标识在等待前保存；停止与注册新任务串行执行；重复停止不会再次取消正在清理的任务 |
| 窗口重搜期间，旧精确评分带上新增耗时，被误当作完整深算证据 | 完成的持续分析保留所有未确认候选的分数界限；缓存拒绝这些候选，实时面板仍展示实际累计工作量 |

## 提速和分析能力

- 同一引擎、完整起始 FEN、着法历史、候选数量和时间预算相同的并发请求合并为一次搜索；调用者拿到独立结果。单个调用取消不会影响其他等待者。
- 训练讲解在前局面候选中已有所走着法及合法应着时，复用同一次搜索的评分和后续，省去第二次搜索。缺少证据时照常补搜；规则终局始终优先。
- 持续研究停止并收到 `bestmove` 后，才能把结果写入有限搜索缓存；完整历史、实际候选覆盖、精确评分和各候选真实耗时均须满足要求。后续提示、训练和全力 AI 可以直接使用已有的更深结果。
- 实时快照只用于面板预填；节点、深度、混合预算和限定着法搜索绕过时间缓存。连续分析不会仅因最佳着法不变而提前停止。

## 本机实测

真实数据见 [原始 JSON](../data/analysis-performance/2026-10-12.json)。训练和并发每个对照各启动新引擎进程，排除跨对照置换表复用；不调用外部大模型，不修改用户棋谱库。训练两侧使用同一步棋，但多线程引擎候选可能变化，因此同时记录命中和回退情况。

| 场景 | 之前 | 当前 | 说明 |
| --- | ---: | ---: | --- |
| 弃马攻象局面的单步训练讲解 | 3001.59 ms / 2 次搜索 | 1503.60 ms / 1 次搜索 | 已有合法候选后续，等待减少约 50% |
| 初始局面，所走着法未进入本次候选 | 3000.48 ms / 2 次搜索 | 3004.16 ms / 2 次搜索 | 正确回退补搜，没有强行复用无关结果 |
| 3 个相同并发分析请求 | 4500.75 ms / 3 次搜索 | 1500.99 ms / 1 次搜索 | 总等待减少约 67% |
| 已完成研究后的分析请求 | 冷搜索 1500.92 ms、深度 20 | 复用 0.07 ms、深度 27 | 前置研究实际耗时 6625.05 ms；复用阶段新增搜索 0 次 |

这是本机单轮耗时记录，跨运行会随候选、系统负载和引擎多线程搜索变化。深算结果的复用有前置计算成本；本轮没有修改 Pikafish 搜索算法，也未通过对局统计测量 Elo 增长。

复现：在仓库根目录运行：

```bash
backend/.venv/bin/python backend/scripts/benchmark_analysis.py
```

输出默认写入 `data/analysis-performance/2026-10-12.json`；可用 `--output` 指定另一个文件，`--research-ms` 改变研究时长。`data/` 为本地证据目录，不进入 Git。
